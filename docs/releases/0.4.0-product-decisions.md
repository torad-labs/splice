| Console, spec §9 | The persistent rail has eight sections, in order: Accounts, Sessions, Teams, Requests, Usage, Models, Compare models, Settings. | Account labels and switching, spec §11 | A chosen name wins; otherwise, a proved account email is the default label. If no email is known, OAuth logins retain the plan word and persistent per-provider ordinal (“Max”, “Max 2”). Email defaults remain defaults until the user renames them; default emails are not saved as chosen names. Account IDs are never shown. Selection is sticky per session and switches between accounts of the same provider when limited. The account with the soonest reset wins (weekly window first, 5-hour window breaks ties; saved order is the alternative). A refused turn may move before its first streamed byte; an explicit login to another account is followed. ([`AccountNaming.kt`](../../features/accounts/src/main/kotlin/splice/accounts/pool/AccountNaming.kt), [`AccountNumbers.kt`](../../features/accounts/src/main/kotlin/splice/accounts/pool/AccountNumbers.kt), spec §11.) | Email-default labels follow the user's latest explicit request and supersede the earlier no-email display rule; this behavior is implementation direction, not a pending release approval. API-key providers remain single-account; cross-provider failover is deferred. | Carry the user-requested email default and chosen-name priority into 0.4.0. |
| Resume, spec §12 | Bare `-c` is resolved before Claude Code receives it, using this head’s session ownership and launch folder. Named `-r` of an eligible other-head transcript makes a copy with a new ID and rewrites the copy for the target head; the source remains intact. An in-client picker or `/resume` is already selected when the hook runs, so the current hook rewrites unsupported model rows in place and saves the original in Splice state. ([`ResumeHookRoute.kt`](../../features/launch/src/main/kotlin/splice/launch/resume/ResumeHookRoute.kt), [`HeadBoundedContinue.kt`](../../integrations/claude-code/src/main/kotlin/splice/client/resume/HeadBoundedContinue.kt), [`SessionIdRetag.kt`](../../integrations/claude-code/src/main/kotlin/splice/client/resume/SessionIdRetag.kt), spec §12.) | The implemented in-client path retains the selected session ID. Rows for models the target head serves remain unchanged. This differs from the copy-on-`-r` path and is listed for owner signoff. | Confirm the current CLI/in-client identity and backup behavior, or revise that implementation before signoff. |
| Project prompts, spec §13 | Prompt layers resolve head → deepest matching project → project-for-head. `append` adds a trailing block; `replace` drops the client prompt and earlier layers; `strip` removes matching paragraphs from the text accumulated at that point. Layers apply on every turn, including compaction; team-slot instructions follow them. ([`SystemPromptLayers.kt`](../../core/src/main/kotlin/splice/core/prompt/SystemPromptLayers.kt#L32), [`HeadSystemPrompt.kt`](../../core/src/main/kotlin/splice/core/prompt/HeadSystemPrompt.kt), spec §13.) | `strip` and prompt performance counters extend the original proposal. Invalid prompt files/configuration and invalid strip patterns fail configuration load; empty strip configuration is rejected. | Keep the three-layer order and mode semantics as built. Confirm that `strip` belongs in 0.4.0. |
| Teams, spec §14 | Teams persist as slots, not processes. Rule-bound slots join the first eligible free slot in team creation order when a session starts on the slot’s head inside the team repo. The page offers Board, By command, By role, and Timeline views; view choice is saved per team. Economics report each slot’s sessions’ 5-hour and 7-day plan-window use, with provider-reported usage shown separately. ([`TeamRuleBinding.kt`](../../features/sessions/src/main/kotlin/splice/sessions/teams/TeamRuleBinding.kt), [`teams.js`](../../app/src/main/resources/console/teams.js#L671), spec §14.) | Rule binding, the additional three views, and per-slot plan-window use were added after the initial Teams scope and are listed for signoff. Splice records composition and observed activity; it does not enforce roles or coordinate members. | Review these additions together. Keep the usage figures distinct from provider usage percentages and retain the no-process-management boundary. |
