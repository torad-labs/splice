## Established mechanisms behind pauses and bursts

1. **The exec program is deliberately invisible during generation.** `ResponsesExecProgress.kt:1–7,39–47` explicitly documents the October 12 product decision: every custom-tool input delta feeds the runtime only. A long script can produce no user-visible output until a callback dispatches. Keepalives preserve transport liveness but show no model content. This is current intended behavior, not a newly found defect.

2. **Streaming execution has several deliberate gates.** `CodeModeStatementParser.kt:84–119` holds the final statement until a following complete token proves its boundary. `StreamingWorkerSession.kt:69–72` defers statements that are not safe with partial source. `StreamingCodeModeLauncher.kt:97–110` defers function-dependent reads because later source can replace declarations. Finally, `CodeModeSourceBuffer.kt:54–64,124–145` stops unread statements after item completion until the response terminal certifies them; `CodeModeStreamingCell.kt:28–34` applies the certification check before exposing calls. A compound or function-heavy program therefore often batches callbacks at EOF even though input was streaming. Existing tests intentionally assert these protections in `CodeModeSourceCertificationTest.kt:51–75,172–189` and `CodeModeStatementBoundaryTest.kt`.

3. **One large summary delta defeats whole-frame pacing.** With cutoff summaries, `ResponsesReasoningFold.kt:90–104,109–118` emits the complete section as one `thinkingDelta`. `DeltaPacer.kt:68–77,138–142` admits the first visible frame after quiet immediately and otherwise budgets frames, not characters. Consequently a multi-kilobyte summary in a single delta appears at once; the pacer can smooth many short deltas, but cannot animate one large one. Whether this user's active configuration selects cutoff is unverified here.

4. **Code mode holds later content for the next callback result request.** `CodeModeStreamingCell.kt:32` detaches the source sink before a `Calls` step publishes. `CodeModeSinkWrites.kt:20–29` queues subsequent source writes; `CodeModeSwitchingSink.kt:72–76` drains them only when the next client request attaches. The hold can last for the tool's execution time, and the queue then arrives as a batch. Queue size is bounded to the 1 MiB frame budget (`CodeModeSinkWrites.kt:26–29`), but duration depends on the next attachment. This ownership rule prevents late source frames from reaching an already completed HTTP response.

5. **Durability is on the visible callback path.** A source record saves before admission (`CodexCodeModeDriver.kt:54–56`); callback issuance saves before `replay` emits tool chips (`CodexCodeModeMachine.kt:122–139`). The journal forces appends/checkpoints (`CodeModeStateJournal.kt:50–75,102–110`). `CodexCodeModeStore.kt:158–172` releases the head-wide registry lock during I/O while the conversation-key transaction remains held. Disk delays can delay callback appearance; their contribution is a hypothesis until measured.

The final socket writer flushes every frame (`ImmediateSseWriter.kt:52–54`), so I found no reintroduced wait-for-next-write flush bug in that layer. Pacing is bounded in elapsed-time policy, and the release loop holds `ClientChannel.writeMutex` while writing its due frames (`ClientChannel.kt:249–254`). Slow socket I/O can still hold this mutex and block producer/pinger work; socket duration is already counted in `write_ms` (`ClientChannel.kt:177–198`). No live slow-socket evidence was inspected.

## Confirmed minor lifecycle gap

`CodexCodeModeMachine.started` retains one timestamp for each script that first advances (`CodexCodeModeMachine.kt:55,79`). Its removals are limited to machine-controlled endings (`:92,175,179,197,225,235`). Autonomous cell parking (`state/CodeModeCellRetention.kt:153–163`), record TTL expiry (`CodexCodeModeSweeper.kt:157–165`), and bridge head stop (`CodexCodeModeBridge.kt:159–166`) close or remove the corresponding state without removing these entries. A later resume can clean some via the machine, but a script whose client never returns has no such path. This is an unbounded accumulation of small record-ID/timestamp entries over bridge lifetime; it is unlikely to explain the current visible stall on its own.

Search evidence: `rg -n '\.started\b|started\.clear|started\.remove|started\.put|internal val started' integrations/providers/codex/src/main integrations/providers/codex/src/test` returned the declaration, insertion, the six listed machine removal sites, one map assertion, and unrelated test-fixture `runtime.started` fields. There is no external lifecycle cleanup of the machine's map in scope. The corresponding clearance relation is `complete: false`.

## Performance hypothesis and limits

`CodeModeSourceCapture.kt:79–85,95–98` reconstructs and UTF-8 encodes the entire accumulated prefix for every delta. `CodeModeSourceBuffer.kt:44–51` checks that prefix again. The parser re-tokenizes the pending suffix on each attempted boundary (`CodeModeStatementParser.kt:84–119,201–226`) and retains both pending and original source. Long indivisible/function-dependent source can therefore do repeated work over a growing suffix. The default source bound is 65,536 characters (`CodexCodeModeBridge.kt:23,54`), which limits the damage; no benchmark here establishes that it creates this user's stalls.

I found no new proven lost-event or duplicate-callback defect in the examined buffer ownership. Existing tests explicitly cover detached draft reset, cumulative witness limits and per-attachment native identity (`CodeModeStreamPortsTest.kt:65–90,124–183`). Failed-drain reattachment and socket backpressure deserve runtime reproduction before being reported as defects. This map does not inspect local Codex source or live settings/logs; those are owned by the parent investigation.
